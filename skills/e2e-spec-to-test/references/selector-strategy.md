# E2E Selector Strategy Guide

The single most important decision in E2E test authoring is selector stability.
Brittle selectors are the #1 reason E2E test suites become unmaintainable.

This guide defines the mandatory selector hierarchy for all tests generated by `tw-ai-toolkit`.

---

## Selector Hierarchy (in priority order)

Apply selectors from top to bottom. Only move to the next level if the previous is unavailable.

### Level 1 — data-testid (preferred)

```typescript
// Playwright
page.getByTestId('submit-order')

// Cypress
cy.getByTestId('submit-order')
// or with Testing Library:
cy.findByTestId('submit-order')
```

**Why:** Completely decoupled from visual style and DOM structure. Only changes when
the QA team explicitly updates it. A `data-testid` change is a deliberate contract change.

**In the component:**
```tsx
<button data-testid="submit-order" onClick={handleSubmit}>
  Place Order
</button>
```

**Rules:**
- Format: `kebab-case`, lowercase, no spaces
- Must describe the element's purpose, not its visual role: `submit-order` not `blue-button`
- Must be unique within the page context (not globally unique — scoped within a section is fine)

---

### Level 2 — ARIA roles and accessible names

```typescript
// Playwright
page.getByRole('button', { name: 'Place Order' })
page.getByLabel('Order amount')
page.getByPlaceholder('Enter amount')

// Cypress (with @testing-library/cypress)
cy.findByRole('button', { name: 'Place Order' })
cy.findByLabelText('Order amount')
```

**Why:** Validates accessibility AND tests behavior. A `getByRole('button', { name: '...' })`
also verifies that the button is keyboard-accessible and has a meaningful label.

**When to use:** When `data-testid` does not exist and adding it is not feasible
(third-party components, legacy HTML).

---

### Level 3 — Visible text content

```typescript
// Playwright
page.getByText('Order confirmed')
page.getByText('Error: invalid amount')

// Cypress
cy.contains('Order confirmed')
cy.findByText('Order confirmed')
```

**Why:** Less stable than ARIA (text can be translated, reformatted, or truncated)
but more stable than CSS selectors.

**When to use:** For asserting output messages, headings, or labels where no better
selector exists. Avoid for interactive elements (buttons, inputs).

---

### Level 4 — CSS selectors (last resort)

```typescript
// Playwright
page.locator('[type="submit"]')    // ✅ attribute selector — acceptable
page.locator('form button')        // ⚠️ structure-dependent — fragile
page.locator('.btn-primary')       // ❌ class name — never use

// Cypress
cy.get('[type="submit"]')          // ✅
cy.get('form > div > button')      // ❌ never use structural selectors
cy.get('.order-button')            // ❌ never use class name selectors
```

**Never use:**
- Class names (`.btn`, `.active`, `.order-form__submit`) — change with UI redesigns
- Structural selectors (`div:nth-child(3)`, `table tr:last-child`) — break on any DOM change
- Generated IDs (`#ember123`, `#react-select-2`) — not stable across renders
- XPath (unless testing a non-web target) — verbose and structure-dependent

## Waiting Strategy

Never use arbitrary time waits. Always wait for observable conditions.

### Playwright

```typescript
// ✅ Wait for navigation
await page.waitForURL('**/order-confirmation/**');

// ✅ Wait for element state
await expect(page.getByTestId('success-banner')).toBeVisible();

// ✅ Wait for network request
const responsePromise = page.waitForResponse('**/api/orders');
await page.getByTestId('submit-order').click();
const response = await responsePromise;
expect(response.status()).toBe(201);

// ❌ Never do this
await page.waitForTimeout(3000);
```

### Cypress

```typescript
// ✅ Wait for alias
cy.intercept('POST', '/api/orders').as('placeOrder');
cy.getByTestId('submit-order').click();
cy.wait('@placeOrder').its('response.statusCode').should('eq', 201);

// ✅ Wait for element
cy.getByTestId('success-banner').should('be.visible');

// ✅ Wait for URL
cy.url().should('include', '/order-confirmation');

// ❌ Never do this
cy.wait(3000);
```

## data-testid Naming Convention

| Element | data-testid pattern | Example |
|---|---|---|
| Submit button for a form | `submit-[form-name]` | `submit-order`, `submit-login` |
| Cancel/close action | `cancel-[context]` | `cancel-order`, `close-modal` |
| Navigation link | `nav-[destination]` | `nav-orders`, `nav-profile` |
| Input field | `input-[field-name]` | `input-amount`, `input-email` |
| Dropdown/select | `select-[field-name]` | `select-currency`, `select-country` |
| Error message | `error-[context]` | `error-amount`, `error-form` |
| Success message | `success-[context]` | `success-order`, `success-banner` |
| Loading indicator | `loading-[context]` | `loading-orders`, `loading-overlay` |
| List/table container | `list-[name]` | `list-orders`, `list-items` |
| Single list item | `item-[name]` | `item-order`, `item-product` |
| Modal/dialog | `modal-[name]` | `modal-confirm`, `modal-edit` |
| Page section/region | `section-[name]` | `section-cart`, `section-summary` |

## When data-testid Does Not Exist

If a required `data-testid` is missing from a component, the generated test includes a TODO:

```typescript
// TODO: add data-testid="submit-order" to <button> in src/orders/OrderForm.tsx
// Current fallback (fragile — replace after adding data-testid):
const submitButton = page.getByRole('button', { name: 'Place Order' });
```

The QA team must add the `data-testid` before the test can be considered stable.
This is intentional: the test serves as documentation of what attributes are expected.

**Recommendation:** Add a PR check that rejects new interactive components
without `data-testid` attributes on key interactive elements.
