# Contributing Guide — Creating and Contributing Components

This guide explains how to create new components, follow conventions,
and contribute them back to the toolkit.

---

## Before You Start

1. Read `AGENTS.md` to understand the toolkit architecture
2. Read this guide fully before writing any code
3. Check `registry.json` — the component you want might already exist
4. Open an issue first for new agents or MCP servers (discuss before building)

---

## Files you must NOT edit manually

These are auto-generated. Editing them by hand will be overwritten on the next sync.

| File | Generated by |
|------|-------------|
| `registry.json` | `scripts/sync_registry.py` |
| `context/snapshot.md` | `scripts/sync-snapshots.sh` |
| `context/snapshots/*.md` | `scripts/sync-snapshots.sh` |
| `context/CHECKPOINT.md` | `scripts/sync-snapshots.sh` |

---

## Component Types and When to Use Each

| Use this | When you want to... |
|---|---|
| **Skill** | Automate one specific, reusable action |
| **Agent** | Orchestrate multiple skills for a complex autonomous task |
| **Prompt** | Provide a reusable, parameterizable prompt template |
| **Rule** | Define behavioral constraints for an AI model |
| **Hook** | Trigger automation on an assistant event |
| **MCP Server** | Integrate an enterprise tool via Model Context Protocol |

**Rule of thumb:** If it does more than one thing, it's probably an agent, not a skill.

## Flow A — Create a component from scratch

### Step 1 — Copy the template

```bash
# Replace <type> with: skills, agents, prompts, rules, hooks, or mcp
cp -r <type>/_template/ <type>/<your-component-name>/
```

### Step 2 — Fill in the definition file

See the frontmatter reference below. Every field marked required must be present.

### Step 3 — Write tests

```bash
cp -r tests/_template/ tests/<your-component-name>/
```

### Step 4 — Sync and validate

```bash
make sync      # regenerates registry.json and context snapshots
make validate  # checks frontmatter and registry sync
```

Fix any errors before opening a PR.

### Step 5 — Open a PR

The CI runs `sync_registry.py` and `validate.py --strict` automatically.

## Flow B — Adopt an external or community component

When an existing external component meets the team's needs, adopt it instead of
building from scratch.

### Acceptance criteria (all required)

| Criterion | Detail |
|-----------|--------|
| **Active source** | Publicly maintained repository (GitHub/GitLab); no anonymous forks |
| **Compatible license** | MIT, Apache 2.0, BSD — no GPL or restrictive licenses |
| **No known vulnerabilities** | Scan with `gitleaks` before adopting |
| **No unaudited dependencies** | Scripts must use only stdlib or packages already in `requirements.txt` |
| **PR review** | At least 1 reviewer in addition to the author |
| **Adapted to standard** | Must be converted to the `skill.md` structure with `tw-*` frontmatter |

### Security scan before adopting

```bash
git clone <source-url> /tmp/candidate
gitleaks detect --source /tmp/candidate --no-banner
# If clean → proceed with adaptation
```

### PR title format

```
feat: adopt <component-name> from <source>
```

Include in the PR description: source URL, version/commit SHA, scan result, changes made.

## Component Naming Conventions

```
Format:     kebab-case
Prefix:     tw- (in invocation and command stubs, NOT in folder name)
Examples:   sync-context, lint-component, onboard-repo

Folder:     skills/sync-context/     (no tw- prefix)
Invoked as: /tw-sync-context         (tw- prefix at invocation)
```

## Skill Frontmatter (`skill.md`)

Every `skill.md` must open with a YAML block:

```yaml
---
name: <skill-name>
description: >
  Trigger-phrase-rich description. Mention what the user says to invoke this.
  Use when the user asks to: ...
  Triggered by phrases like "...", "...", "...".
  NOT for: ...
status: stable
version_added: v0.1.0
compatible_with:
  claude_code: full | partial | none
  cursor: full | partial | none
  codex: full | partial | none
parameters:
  - name: target
    type: string
    required: true
    default: ""
    description: Description of this parameter
tags:
  - example
invocation: tw-<skill-name>
---
```

### Field reference

| Field | Required | Values / Notes |
|-------|----------|----------------|
| `name` | yes | kebab-case, must match directory name |
| `description` | yes | "trigger-phrase-rich" — include trigger phrases and NOT-for cases |
| `status` | yes | `stable` / `beta` / `experimental` / `deprecated` |
| `version_added` | yes | semver, e.g. `v0.1.0` |
| `compatible_with` | yes | dict with tool names as keys; values: `full` / `partial` / `none` |
| `parameters` | no | list of parameter objects (name, type, required, default, description) |
| `tags` | yes | list of lowercase strings |
| `invocation` | yes | `tw-<skill-name>` — no leading slash |

### Writing good descriptions

The description field is what AI models use to decide when to invoke a skill automatically.
Make it specific:

```yaml
description: >
  Use when the user asks to: sync the toolkit registry, regenerate context snapshots,
  or update the component index. Triggered by phrases like "sync context",
  "registry is stale", "update snapshots".
  NOT for: installing the toolkit in a new repo (use install-toolkit).
```

## Skill Definition Body (`skill.md`)

Required sections:

```markdown
## Description
One to three paragraphs. What it does and what the output looks like.

## When to Use
Specific trigger conditions. When should the AI invoke this?

## Parameters
Table of accepted parameters (or omit if none).

## Instructions
The actual prompt the AI model will follow. Step-by-step, specific.

## Examples
At least one invocation example with expected output.

## Dependencies
Other skills or external tools required (or "none").
```

## Agent Definition (`agent.md`)

Required fields in frontmatter: `name`, `description`, `status`, `version_added`,
`compatible_with`, `tags`, `invocation`.

Required body sections: `## Description`, `## Trigger`, `## Skills Used`, `## Flow`, `## Outputs`.

## Deprecating a Component

1. Set `status: deprecated` in the definition file
2. Add `deprecated_since: <version>` and `removed_in: <next-major>`
3. Add a `replacement: <component-name>` field
4. Run `make sync`
5. Add an entry to `CHANGELOG.md`
6. The component continues to work but will warn users when invoked

**Never remove a component in a minor or patch release.**

## After Every Component Change

```bash
make sync      # regenerates registry.json and context snapshots
make validate  # validates frontmatter and registry sync
```

The pre-commit hook (`.git/hooks/pre-commit`) runs sync automatically when component
files are staged. Install it once per clone:

```bash
bash scripts/install-git-hooks.sh
```

## Agent Definition (`agent.md`)

Required fields:

```markdown
# <agent-name>

## Description
[REQUIRED] What autonomous task this agent accomplishes.

## Trigger
[REQUIRED] When should this agent be invoked?

## Skills Used
[REQUIRED] List of skills this agent orchestrates.
- /tw-skill-one
- /tw-skill-two

## Flow
[REQUIRED] Step-by-step description of the agent's execution flow.

## Inputs
[REQUIRED if any] What the agent needs to start.

## Outputs
[REQUIRED] What the agent produces when done.

## Compatible With
[REQUIRED] Same format as skill.

## Status
[REQUIRED] stable | deprecated | experimental
```

## Prompt Definition (`prompt.md`)

```markdown

## Description
[REQUIRED] What this prompt template is for.

## Parameters
[REQUIRED if any] Variables in the template use {{double_braces}}.

[REQUIRED] The actual prompt. Use {{variable}} for parameters.

## Example
[REQUIRED] Filled example with real values.

## Status
[REQUIRED] stable | deprecated | experimental
```

## Hook Definition (`hook.md`)

```markdown
# <hook-name>

## Description
[REQUIRED] What this hook does.

## Event
[REQUIRED] Which assistant event triggers this hook.
Examples: PreToolUse, PostToolUse, Stop, Notification

## Condition
[OPTIONAL] Additional condition to filter when the hook fires.

## Action
[REQUIRED] The command or script executed when the hook fires.

## Configuration
[REQUIRED] How to add this hook to settings.json.

## Status
[REQUIRED] stable | deprecated | experimental
```

## Deprecating a Component

When a component needs to be removed or replaced:

1. Change its `Status` field to `deprecated`
2. Add a `Deprecated Since` field with the current version
3. Add a `Removed In` field with the planned major version for removal
4. Add a `Replacement` field pointing to the new component
5. Run `sync-registry.sh` to update `registry.json`
6. Add an entry to `CHANGELOG.md`

The component will continue to work but will warn users when invoked.

**Never remove a component in a minor or patch release.**

---

## Code Quality Standards

- All content in English
- No secrets or credentials in component files
- Every component must have at least one test case
- Skills must be atomic (one responsibility)
- Instructions must be specific enough that two different models produce consistent output
- Components must declare their compatibility explicitly
